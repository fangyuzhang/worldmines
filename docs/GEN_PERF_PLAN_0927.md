# 关卡生成器性能优化·系统性方案（2026-09-27 版）

> 本文档是「再检查分析一遍」的交付物。**所有数字均为实测**（探针产物见 `tools/_stage*_out.txt`、
> `tools/_p0_verify.log`、`tools/_golden_*.jsonl`、服务器 `/root/thin_fill_plan.log` 与
> `user://*/issues*.jsonl`），不是估算。凡证据不足处**显式标注「证据不足」**并给出最小验证手段。
>
> 红线（不可用速度交换）：**R01 序贯可解（无猜可推完）**、**R04 构造式生成（禁暴力重试/暴力生成/暴力解题）**、
> **难度承诺不漂移**、**机制不重复**。本方案所有项均在此约束下评估。

## 0. 结论摘要

1. **性能面已收敛的判断在旧根因模型下成立，但旧模型是错的。** 前一轮评审（r4）判 CONVERGED 的前提是
   「限速主因 = CP-SAT 单次求解无界」。今日抓现场证明：挂死进程 **`State: S (sleeping)` /
   `wchan=futex_wait_queue` / 13 线程 / CPU 均值 8.4% / `maj_flt=0`** ⇒ 主因是 **native 侧线程死锁（futex 丢唤醒）**。
   这把「靠墙钟上限兜住」整条防线判为无效，也解释了历史「6 子进程同时挂死、CPU 近 0」。
2. **但死锁不改变"求解耗时的**主分布**"**：在**不挂死**的正常路径上，94.2% 仍花在
   `RuleSolver.cs:152-185` 的 assumption 探测上。故**算法级杠杆仍集中在"减少探测次数/复用探测结果"**，
   而死锁是**独立的可用性（availability）问题**，只能靠进程外兜底 + 根因实验，不能靠参数上限。
3. **本轮新发现的最大零质量风险杠杆**：复合档实测 `peak_miss = 25/45`（**56% 的候选因"难度峰值不在目标窗口"被丢弃**）。
   这些候选**本身是合规关卡**，只是被归到了错误档。⇒「跨档候选路由」可把同一批算力产出提高近一倍，
   且**关卡内容一字不改**（只改归属），R01/R04/难度全不受影响。**这是优先级最高的新项。**
4. 结构上有 105 片 hard 薄单元**数学/结构不可达**（如 `classic+s3@8` 实测 0/5、每个 seed 打满 90s 墙钟），
   属**排产剔除**项，不属优化项。

## 2. 根因拆解（现象 → 底层根因 → 证据）与止损/深水边界

> 边界定义：**止损组 = 不改生成算法、不改难度判据、可独立回滚**；
> **深水项 = 触碰求解/剪枝/布雷策略，必须 A/B + 质量网护航**。

| # | 现象 | **底层根因**（不是现象复述） | 证据 | 归类 |
|---|---|---|---|---|
| R1 | 进程"卡住"数小时～数天，看门狗没抓到 | **native 线程死锁（futex 丢唤醒）**。主线程在等一个永不到来的唤醒 ⇒ ① 求解器内部墙钟/确定性工作量上限**永不触发**（死锁线程不看计时器）；② TERM **无效**（卡在 futex 的线程不处理信号）；③ CPU **低**（在等不在算），而旧看门狗判据要求 `CPU ≥ 80%` ⇒ **结构性抓不到** | `/proc/<pid>/`: `State: S`, `wchan=futex_wait_queue`, 13 threads, CPU 8.4%, `maj_flt=0`；实测 TERM 无效→KILL 生效 | **止损**（兜底）+ **深水**（消除） |
| R2 | 单候选耗时长（复合档更甚） | 探测次数 × 每次 Solve。`FindForcedCells` = 1 次首解 + **O(自由格) 次 assumption 探测**，每轮≈18.6 次 Solve；删线索 O(n) 条 × 序贯 O(轮) ⇒ 累计量级放大 | `RuleSolver.cs:152-185`、`_stage0b_out.txt` | **深水** |
| R3 | 反复"重试/give-up" | 计划按**日志是否出现 done 行**判停，而 `run_window_production.sh` 是 `set -e` ⇒ 非零退出时 done 行永不打印 ⇒ **"正常零增量收尾"与"被杀"被混为一谈**，白跑 3 次 | 实测 104 条 retry/give-up（历史）；改正后 `note=0` 且语义分层 | **止损（已完成）** |
| R4 | 同一 "77% 组合层" 长期 0 产出 | 不是引擎不支持，而是 **① 计划未列 spec；② 更隐蔽：复合档的隐藏态从未初始化**（`globals` 非空 ⇒ 走全局规则的 `place_mines`，线索规则的 `place_mines` 不被调用 ⇒ 隐藏态为空或残留上一盘），而**四处门禁全部放行**（线索值现算 + 求解器读同一份状态 ⇒ 自洽）⇒ 产出"自述 o4、实为 classic"的退化关 | 实测：全新会话 `_r2=0`（应 16）；污染态跨 seed 同集；7×7 盘落盘 16 格而 `_k_of(7,7)=12` | **止损（P0 已完成）** |
| R5 | 合成大量候选却产出很少 | **难度峰值窗口过滤**：候选合法但峰值不在目标窗（hard@8 窗口 6-20）⇒ 直接丢弃。实测 **peak_miss=25/45 = 56%** | 首个复合单元的 `unit_done` + `peak_hist` | **止损（新杠杆）** |
| R6 | 某些单元"永远打不满"，白烧整轮 | **结构不可达**（非参数问题）：`classic+s3@8x8/26` 实测 **0/5，每个 seed 打满 90 s**（`prune_timeout=1, verify_fail=1`）；同类 hard 薄片 105 片 | 黄金快照 + 服务器日志 | **止损（排产剔除）** |
| R7 | 独立复核吃掉可观墙钟 | **同一盘被两套模型推两遍**：生成期 `_solve_rules_stepwise`（松弛模型）+ `ProofLog.build`（玩家视角 + HintSolver，**唯一独立复核**）13.4–18.5% | `_stage0c_s2.log` | **止损（共享中间量）** |
| R8 | 删线索结果重跑会变 | 删线索**按墙钟判停** ⇒ 机器快慢/负载影响停在哪一步 ⇒ 同 seed 两次重跑 clue_count 波动 | 已文档化的残余风险；`prune_timeout` 留痕 | **深水** |
| R9 | 隐性重复关卡风险 | 现有指纹去重**只在单元内**；库级并入签名曾**不含几何**导致 shape 与 classic 误并（已修）⇒ 跨席位/跨尺寸规范化去重仍是空白 | `merge_lib_into_src.py` 假匹配事故 | **止损（加固）** |
| R10 | CPU 利用率仅 ~50% | 计划 `wait_core` 按「全机 Godot 数 ≥ nproc 就等」串行；2 核但常只 1 个 Godot（load 1.03/2.0）。**不可贸然双启**：双计划会互锁（各起一个 Godot 后互相等），双 Godot 在 1.9 GB 上有 OOM 风险 | `uptime` load 1.03；1.9 GB 内存 | **止损（受资源约束）** |

**止损/深水边界**：R1(兜底)/R3/R4/R5/R6/R7/R9/R10 = 止损组，**不触碰求解与难度判据**；
R2/R8 与 R1(根因消除) = 深水组，**必须 A/B + 黄金网 + 峰值直方图护航**。

## 3. 方案集与评估

> 评估口径：工作量（人时）、风险、预期收益、**是否影响难度/质量**。高风险项附风险点与验证手段。
> 收益基线：P3 缺口 117,100 关 ≈ **1,300–2,000 核时**。

### 3.1 止损组

**S1 跨档候选路由（优先级 No.1，新发现）**
- 做法：生成时记录每个候选的**实测峰值**；落在 easy/normal/hard 任一窗口的候选**归入对应档**，而不是丢弃。
- 工作量：**中**（改 `batch_all_variants.gd` 的接收逻辑 + 落盘归属 + 单元记账）。
- 风险：**低**。风险点：① 若三档窗口**重叠**，归属需唯一化规则；② 可能把"供过于求的档"塞爆而"稀缺档"仍空 ⇒ 需按目标配额优先分配。
- 收益：直接攻击实测 **56% peak_miss**。理论上同一批算力产出可提升 **≈1.5–2×**（取决于窗口覆盖率）。
- 难度/质量：**无影响**——关卡内容一字不改，只改归属；`check_lib_tiers.py` 逐关 0 错档由构造保证。
- 验证手段：先跑**离线统计**——取已产出的 `peak_hist`，算「按窗口分区后各档可得数」；再 A/B 两个单元
  （单元 A 原逻辑 vs 单元 B 路由逻辑），比 `made/cost_s` 与 `by_tier` 分布，**关卡级 diff 应为空**。

**S2 `ProofLog.build` 归因 + 中间量共享（13.4–18.5%）**
- 做法：把 proof 耗时纳入阶段统计（可观测）；在**不取代** `ProofLog.build` 的前提下，共享 `build_spec`/规范化解码等无争议中间量。
- 工作量：小～中。
- 风险：中。风险点：**任何"复用生成期结论"都可能让门禁退化为自洽检查**（r4 N4 明令）。
- 收益：先拿到可观测（0 直接收益），共享最多吃掉一部分 13–18%。
- 难度/质量：**必须不降**——金丝雀规则：含隐藏态规则/新放开复合档 **100% 走完整 ProofLog.build**。
- 验证：金丝雀单元的 `proof_fail` 必须仍为 0；抽样 30 关做"完整 vs 共享"双跑比对，结论必须一致。

**S3 结构不可达单元的排产剔除（R6）**
- 做法：入库前对每个 `(combo, size, tier)` 跑一次**廉价预筛**（`RuleFeasibility.query` + `RuleSignature.compat_all` +
  小样本峰值探测），不可达的直接从计划里删掉并**记入规格说明**。
- 工作量：小。
- 风险：**低**。风险点：预筛用"小样本"判不可达**可能误杀**真可达单元 ⇒ 判据必须保守（只剔除"数学不可行"与"实测 N 个 seed 全打满墙钟"两类）。
- 收益：`classic+s3@8` 一类每 seed 白烧 90 s；105 片 hard 薄片若半数属此类，单轮可省**数十分钟～数小时**。
- 难度/质量：无影响（不产出任何关卡）。
- 验证：剔除清单需附**不可达证据**（`is_feasible=false` 或 ≥5 seed 全超时）；剔除后计划轮数与预期一致。

**S4 计划级参数浪费审计（`attempts` / `timeout_ms` / `per_tier` / seed 扫描）**
- 做法：从 `unit_done` 统计 `tried → made` 收敛曲线，判断 `attempts` 是否过大（45 次尝试出 20 ⇒ 后续 25 次是否低收益）。
- 工作量：小（纯统计 + 调参）。
- 风险：低。风险点：调小 `attempts` 会降低难产单元的达成率 ⇒ 需按单元类型分档设置。
- 收益：减少"低收益长尾尝试"的机时占用。
- 验证：同单元 A/B（`attempts` 原值 vs 收敛点值），比 `made` 与 `cost_s`。

**S5 死锁兜底强化（R1 兜底，已完成，纳入监控）**
- 已落地：看门狗判据改为**零产出为主判据**（CPU 仅分类取证）、**TERM→grace→KILL(9)** 升级、覆盖"启动即挂死"；
  长任务统一 `timeout -k`（裸 `timeout` 只发 TERM，对 futex 死锁无效且自身会被卡住）。
- 待补：**看门狗自监控**（它死了没人知道）——加心跳文件 + 外部检查（可由计划的每轮 init 顺带检查）。
- 验证：制造一次假挂死（`kill -STOP`），看门狗须在 `STALL_MIN`+宽容期内取证并 KILL 成功。

**S6 库级去重加固（R9）**
- 做法：库级签名**必须含几何/形状标识**（已有事故教训），并新增**跨尺寸/跨席位规范化**去重（D4 对称群归一）。
- 工作量：中。风险：低（只拒绝入库，不改生成）。
- 验证：`levels_lib` 全量重扫，重复数应为 0；并做一次"人工构造重复盘"注入测试，确认能被拒。

**S7 资源调度（R10）**
- 做法：评估「单 Godot 进程内 `num_search_workers=2`」是否比「双 Godot」更安全（共享同一 `.godot` 缓存，无双进程争用）。
- 工作量：小（改一处 spec 透传）。风险：**中高**——`num_workers>1` 曾致**非确定性**（同 seed 不同盘）与长尾挂死，项目 09-24 刻意改回 1。
- 收益：CPU 利用率 50%→接近 100%（可行性待测）。
- 验证：**同 seed 同参数两次重跑逐字节比对**（必须一致）；`load` 与挂死率对比。**非确定性不可接受**，若命中即回滚。

### 3.2 深水组（算法深度优化）

**D1 探测次数削减（R2，收益上限最大）**
- 方案 A：**一轮内 memo**——同一轮内多格探测共享已解模型（当前每格独立 Solve）。
- 方案 B：**跨轮增量**——上一轮的强制格结论作为本轮已知量注入（当前每轮从零开始）。
- 方案 C：**探测预算的边际收益调度**——优先探测"最可能推出新结论"的格（用约束依赖度排序），而非自然序。
- 工作量：A 小-中；B 中高；C 中。
- 风险：**高**。风险点：任何减少探测都可能**误报强制格**（比漏报危险得多：漏报=拒收，误报=产出坏关）。
  ⇒ **只允许"保守方向"优化**（宁可少报）。
- 收益：94.2% 的耗时基座，A+B 理想可削 30–50%。
- 难度/质量：**必须零退化**。验证：① 黄金网既有 25 行**逐字节不变**；② 随机 200 盘"新旧版强制格集合"逐格比对，**新集合 ⊆ 旧集合**（保守性证明）；③ `verify_fail` 不得上升。
- **高风险标注**：`RuleSolver.cs:158-164` 已有反例（classic_07）证明"未被约束引用的格"**不能**剪——同类"看似安全的剪枝"必须先找反例。

**D2 删线索判停：墙钟 → 步数/收益（R8）**
- 做法：以"删一格后是否仍可解 + 收益是否为正"为判据，替代墙钟；使同 seed 重跑**逐字节可复现**。
- 工作量：中。风险：中高（会改变产出分布）。验证：同 seed 两次重跑比对 `clue_count`/峰值；
  **峰值直方图 A/B**（难度漂移的直接判据）。

**D3 死锁根因消除（R1 根因）**
- 方案 A：`cp_model_presolve:false` A/B（同一病态实例看是否仍卡在同一 `wchan`）。
- 方案 B：worker/线程模型调整（`num_search_workers`、`num_workers` 与 presolve 线程数的关系）。
- 方案 C：OR-Tools 版本升级/构建参数核查。
- 工作量：A 小（加一个 spec 键 + 重建 dll）；B 中；C 高。
- 风险：A/B 可能改变求解耗时（需 A/B 量化）；C 影响面大。
- 收益：把"只能 KILL 兜底"变成"可消除"——是**可用性**层面的根本改善（不再丢轮、不再锁死计划）。
- 验证：用**已知病态实例**重复 N=20 次，统计挂死率（当前基线需先测）；改动后挂死率应显著下降。

**D4 生成期内容去重（对称群规范化）**
- 做法：用 `RuleSignature.SYM_D4` 把盘面归一化 → 规范哈希 → 与"本批已产 + 库内已有"比对。
- 工作量：中。风险：低（只拒绝产出）。收益：消隐性重复、降下游 merge 成本。
- 验证：注入已知对称等价盘，必须被识别为重复；库内全量重扫重复数不变。

## 4. 验证体系

### 4.1 优化前后对比指标（必须全量采集）
| 类别 | 指标 | 采集点 |
|---|---|---|
| 产出速率 | **关/核时**（按 combo/size/tier 分桶）、`unit_done.cost_s`、`made` | `issues*.jsonl` → 聚合脚本 |
| 废品率 | `(tried-made)/tried`、**`peak_miss`**、`verify_fail`、`brep_fail`、`empty`、`full_stall`、`timeout` | 同上 |
| 重复关卡 | 库级签名（**含几何**）冲突数、跨单元/跨尺寸规范化重复数 | `levels_lib` 全量扫描 |
| CPU 利用率 | `load average / nproc`、Godot 进程数、`wait_core` 等待时长占比 | `uptime` + 计划日志时间戳 |

### 10.1 我方被推翻：本文件 §2 表中 R2 相关的一句归因是**方向错的**
原写「`_prune_clues_rules` 带 deadline 易过度删线索导致 `verify_fail`」。**错。**
证据 `core/puzzle_generator.gd:880-888`：到期即 `return` 并置 `state["prune_timeout"]=true`；且删除只在 `_solve_rules_stepwise` 通过时才保留（`:905-912`）⇒
偏差方向是**"删少了"**（线索更多 ⇒ 盘更简单），且非确定性只影响**重跑波动**。`verify_fail` 来自 step-4 自身 deadline 分支（`:960-962`）。
⇒ **D2 的收益必须与"重跑可复现性"绑定，不能记在 verify_fail 上。**

### 10.2 r5 被推翻（我反核成功）——两条，都属于"决定性分诊"
1. **「主挂死类 = Godot mono 关机竞态，与 CP-SAT 无关」不成立于本例。**
   实测：换版前镜像 `/root/backup_20260927_201737/tools/batch_all_variants.gd`（mtime **09-22**）**已含兜底**
   （`CliShutdown=7 / request_exit=5 / CliShutdown.poll=1`），且 `tools/cli_shutdown.gd` 自 **09-11 16:05** 就在服务器。
   ⇒ 那轮挂死是**带着 CliShutdown 仍挂**。按 r5 自己给的判据：「含却仍挂 ⇒ 挂在 `_arm_watchdog` 之前」。
   **更精确的定位（本轮新证据）**：挂死日志**已打印到 `:881` 的「事件记录」行**，而 `:882` 就是 `request_exit(0)`——
   但那只是**登记**；真正的 `_arm_watchdog()`（起 `sleep 2; kill -9` 子进程）+ `tree.quit()` 发生在 `poll()` 的**第 3 帧**。
   ⇒ **挂死点在「request_exit 之后、watchdog arm 之前」：兜底根本没装上。** 这是比"关机竞态 vs CP-SAT"更本质的结论。
2. **「13 线程 = Godot mono 基线（与 CP-SAT 无关）」不成立。**
   实测：**空闲** headless Godot = **1 线程**（RSS 2.1 MB）；**生成中** = **11 线程**（`stat=Rl`, `wchan=0`, RSS 251 MB）。

### 10.3 接受（r5 的正确项）

## 12. 第三轮：读码核实 + 我新读出的一条修法

### 12.1 已核实 r5 §2(c)（读 `tools/batch_all_variants.gd:700-800`）
seed 循环的真实顺序：
```
:718 generate_with_rules(...)                     ← 全额生成代价（o4@8≈17.1s；9×9 系数 3000 ⇒ 243s/候选）
:748-763 峰值不在窗口 → peak_miss 拒收             ← 若已见峰值全在窗口同侧，达 _stall_max 才提前 break

:791-797 单元内指纹去重 ; :798+ 相似度门
```
⇒ **"先生成、后判档满"确认成立**：最坏 60 次全额生成被丢弃（o4@8 ⇒ ~17 分钟/单元；9×9 ⇒ 最坏 **~4 小时/单元**）。记作浪费类别 **W1**。

### 12.2 **新增修法（我读码得出，r5 未提）：把"档满"判定前移到生成之前 ⇒ 消除 W1**
**依据**：三档窗口互斥且各 run 的窗口就是**某一档的区间**（`tools/thin_cells.py` 的 `WINDOW` 由 `core/difficulty.gd:90-95` 派生）
⇒ 窗口模式下 `tier_of_peak()` 对窗口内**任意** peak 都返回**同一个档**。
⇒ 一旦该档 `made_by_tier[tier] >= _per_tier`，**后续任何落在窗口内的候选都不可能被接收**（窗口外的本来也拒收）
⇒ 可在循环开头直接 `break`，**不必先花掉生成代价**。
**等价性**：最终产出与现状**完全一致**（现状也是每个候选都在 `:778-782` 被丢弃），只是不再付生成代价。**零质量风险、不碰难度判据。**
**守卫（必须）**：仅当 `_peak_window` **完全落在单个档的区间内**时才允许前移；手动传入跨档窗口（如 `2-20`）时不得前移。
**收益**：W1 最坏 4 小时/单元 → **0**。
**验证**：同单元 A/B（前移开/关）比较 `made`/产物文件名集合**完全一致**、`tried` 下降；黄金网逐字节不变；单测全绿。

| 浪费 | 修法 | 收益 | 风险 |
|---|---|---|---|
| **W1** 档满后全价生成 | §12.2 判定前移 | 最坏 4h/单元 → 0 | 无（等价，附守卫） |
| **W2** peak_miss | S1 跨档路由（§11.2/11.3/11.4） | **≤1.55×**（受 [2,20] 占比约束） | 低（须先修 `window_bad` 冲突 + 缺口记账） |

| 生成器在该组合的 `t_prune_ms` | **90080ms**（`prune_tries=31` ⇒ 单次试探 ≈ **2.9s**） |
| 差距 | **≈ 36×（单次）／≈ 1000×（总量）** |

⇒ **90s 完全无法用"演绎本身贵"解释**。若每次试探都是 80ms，31 次 = **2.5s**，而不是 90s。
⇒ 因此 90s 必然来自**"删掉一条线索之后的子集演绎"**（或另一处）——即 `A\{p}` 上的演绎比 `A` 上贵 36 倍。这与直觉相反（约束更少 ⇒ 解空间更大 ⇒ **强制格更少、更容易"卡住"**，但也可能**更难被判出强制格**，从而每格探测都跑到预算上限）。
⇒ **这直接决定推论 (i) 的价值**：若贵在子集演绎上，那么 (i)（"逐轮只探测 `D_A(r)` 内的格"）不只是省 59% 探测，而**可能正是解释并消掉那 36× 的钥匙**。

### 15.4 下一步实验（最小、决定性）
给 `_stuck_probe.gd` 加 `--subsets` 模式：对同一盘的 `A\{p}`（逐个 p）各跑一次演绎，报每次耗时与"是否卡住"。
- 若子集演绎 ≈ 2.9s 而全集 ≈ 80ms ⇒ 证实上述猜想 ⇒ **优先做 (i)**（并可用 (i) 把子集演绎压回毫秒级）。
- 若子集演绎也 ≈ 80ms ⇒ 90s 来自别处（如 `build_spec` 在删线索后重建 IR、或 CP-SAT 特定实例病态）⇒ 需另找靶子。
**在该实验出结论前，不要再对 `classic+s3@8` 类单元做任何"加速"改造**（避免优化错对象）。

## 16. 该实验已完成：**1000× 的成因找到了，(i) 得到机制级证据**

### 16.1 子集诊断实测（`classic+s3@8/26`，同一进程）
| 演绎对象 | 线索数 | 耗时 | 结论 |
|---|---|---|---|
| **全量 A** | 38 | **155ms**（seed2 132ms） | 第 1 轮就有大量强制格 ⇒ 轮数少 ⇒ 便宜 |
| `A\{p}` | **37** | **579ms**（3.7×） | 只少**一条**线索就显著变贵 |
| 同上，换 p | 37 | 750 / 1047 / 1162 / **1253ms**（最高 8×） | 且**递增** |
| 全部子集 | — | **仍 `ok=true`**（可推完） | 不是"卡住"，是"变贵" |

### 16.2 机制解释（两段叠加，与实测完全吻合）
1. **线索越少 ⇒ 每轮强制格越少/越难判 ⇒ 轮数↑、每轮的 assumption 探测数↑**（探测成本 = `O(每轮自由格数)`）。
   ⇒ 实测：去掉**一条**线索，代价即涨 3.7–8×。
2. **`_prune_sequential` 成功即"保留删除"**（`:896` `active.erase(p)` + `:905-911` 通过则 `continue` 不回滚）
   ⇒ `active` 在 prune 过程中**单调缩小**（实测该组合 `prune_ok=25`，即从 38 条缩到 **13 条**）
   ⇒ 越到后面，演绎跑在**越稀疏**的盘上 ⇒ 单次代价从 0.6s 涨到数秒
   ⇒ **31 次试探累计 ≈ 90s，完全得到解释**（不再有任何"未知黑洞"）。

### 16.3 结论：**推论 (i) 是唯一对症的杠杆，且现在有机制级证据**
贵的根源是「**每轮对 `O(自由格)` 个格做 assumption 探测**」，而**自由格数随删线索而增长**。
⇒ (i)（A 演绎一次、记下逐轮 `D_A(r)`，此后子集演绎第 r 轮**只探测 `D_A(r)` 内的格**）**恰好切在这个增长点上**：
`forced_B(r) ⊆ D_A(r)`，故白名单外的格**可证非强制**，探测它们纯属浪费。
⇒ 这不是"省 59%"那种统计收益，而是**掐住成本随稀疏度增长的机制**。

### 16.4 收益重估（上修）
先前按"第 1 轮占 59% 探测"估 **30–50%**；按机制重估：若 `|D_A(r)|` 为个位数而每轮自由格为数十，
则子集演绎可回落到接近全集量级（实测目标：0.6–1.3s → **<0.2s**）⇒ **prune 总量有望削 60–80%**，
且对"删到后期"的尝试收益最大（正是现在最贵的部分）。

## 23. 09-28 深查的最终结论（**含对 §21.5 的推翻，务必读**）

### 23.1 **系统性事实（今天才查到）：Godot `-s` 运行不会重建 C# 程序集**
`世界扫雷 (Copy).dll`（本地）与 `wm_server.dll`（服务器）**都不随 `solver/*.cs` 变更重建**：
- 本地：`solver/RuleSolver.cs` 早上 14:55 改动、dll 同刻 → 之后我改的 C#（白名单）**从未生效**；
- 服务器：源码 Sep 28 12:26、dll 仍 Sep 27 15:07（`upgrade_code.sh` 的"无条件重建"预期不成立）。

**要解决的问题**（用户点名，三件同源）：

| # | 现象 | 根因 |
|---|---|---|
| 1 | 异形盘可用、变体可用，组合却被判「不可行」 | 判据层按**矩形模型**算（中轴整除 / 骨牌数 / D4 对称），异形盘上必然误判 |

**方案要点**：

- **判据与生成期共用同一份"带拓扑的 spec"**：新增 `RuleFeasibility.query_topo / resolve_mines_topo`
  （`core/rule_feasibility.gd:58-107`）与 `RuleOracle` 的 `topology` 透传；不变量

  邻接表稳定哈希，FNV-1a 自实现）拼进缓存键；`null`（矩形）用稳定占位串 `rect:null`，
  矩形盘另拼 `rect:WxH`。
- **WARN 不 FORBID**：`RuleSignature.compat_all(ids, size, mines, cells)` 新增 `cells` 维
  （`core/rule_signature.gd:202-241`）——异形盘（存活格 ≠ 包围盒面积）上几何依赖项降级 WARN
  并写明原因「异形盘不适用」，**绝不 FORBID**；不传 `cells` 时逐例与改动前一致（兼容铁律）。
- **能力声明不静默降级**：`RulePlugin.geometry_kind()`（`core/rule_plugin.gd:47-58`）默认
  `GEO_RECT_ONLY` = 今天的行为；生成期改按 `supports_topology()` 门控，不满足时
  **回退 classic 并大声告警**（`core/puzzle_generator.gd:431-444`），禁止静默降级。

  - `core/adjacency_builder.gd`：多边形 → 邻接（共边判据 + 统计 + `audit()`），

    结论行 `__SPEC_VERDICT__`；几何不适用只报「不适用（原因）」，**不打印「不可行」**。
  - `test/unit/test_topology_matrix.gd`：3 类棋盘 × 4 类算子 = 12 格，每格只允许

    也必须判「不适用」（原因=棋盘未提供方向语义标注）。
